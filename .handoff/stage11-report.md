# Отчёт этапа 11 — Адаптивное расписание сканирования (ТЗ §10)

Дата: 2026-08-31. Команды: `pb schedule show | run | init-windows`
(см. «Результаты на реальных данных»).

## Реализовано

### 1. Пакет `internal/schedule/` — модель расписания (ТЗ §10.2–10.5)

**Файлы:**

| Файл | Содержимое |
|---|---|
| `schedule.go` | `Settings` (параметры из конфига), `SettingsFrom`, `TZ` (IANA-пояс страны объявления), `SlotKey` («dow-hour»), `WindowHours` |
| `spec.go` | `ParseSpec("a-b,c",min,max)` — разбор списков дней/часов для init-windows |
| `yield.go` | `RecordYield` (выход полных сканов в `scan_yield`), `SlotAgg`, `TotalScans`, `SlotYields` (окно скользящего среднего) |
| `weights.go` | `Window`, `windowWeights` (чистая функция), `ComputeWeights` (веса + запись в `scan_windows.weight` для аудита) |
| `plan.go` | `Option`, `nextSearchConfig` (round-robin), `Plan` — что сканировать сейчас |
| `backoff.go` | `BackoffDuration` (чистая), `ApplyBackoff`, `NoteSuccess`, `RecoverCooldowns`, `LoadSourceStates`, `EffectiveCap`, `ScansThisHour` |
| `schedule_test.go` | 9 unit-тестов (без БД) |

**Слоты и пояса (ТЗ §10.2, §10.3).** Слот — (день недели, час) в
**часовом поясе страны объявления** (`schedule.country_timezones` в
конфиге, TЗ §10.2: «пик размещения в Праге привязан к рабочему дню
Праги», не сервера). Скан записывается в слот своего времени начала.
Сервер работает в UTC; окна сравниваются уже переведённые в пояс страны.

**Адаптация по выходу (ТЗ §10.3).** `scan_yield` — новые объекты на
скан по (источник, слот, день); окно скользящего среднего
`ma_window_days` дней. Веса окон:
`weight = ε + (1−ε)·(avg/maxAvg)`, где avg — среднее новых объектов на
скан по всем слотам окна (пул по слотам, а не среднее средних: слоты с
большим числом сканов имеют больший голос). `ε`
(`exploration_fraction`) — доля бюджета на исследование: окно с нулевым
(или не наблюдавшимся) выходом не отключается насовсем (ТЗ §10.3:
«слот не отключается насовсем»).

**Честное ограничение (ТЗ §10.5).** Пока по источнику накоплено меньше
`min_obs_for_tuning` полных сканов — расписание работает на равных
консервативных весах 1.0 и помечается `warming_up`; `pb schedule show`
выводит флаг явно. Ранняя «адаптация» не выдаётся за настроенную по
статистике.

**Бэкофф (ТЗ §10.4).** Капча/429 → источник немедленно `cooldown`:
`strikes + 1`, кулдаун `base · multiplier^(strikes−1)` с потолком
`max` (считается в float64 — при больших strikes произведение
переполнит `time.Duration` и даст отрицательный «кулдаун»),
`rate_factor` падает вдвое (не ниже `min_rate_factor`). `rate_factor` —
множитель потолка: эффективный потолок = `floor(max_requests_per_hour
× rate_factor)` (округление ВНИЗ: потолок не превышается ни при каком
выходе). Запуск скана в кулдауне отклонён до истечения (без
`scan_run`, без изменения strikes). Истечение — `RecoverCooldowns`
(вызывается в начале каждого `Plan` и возвращает истёкшие кулдауны в
`active`; ручные состояния `disabled`/`blocked` не трогает).
**Восстановление постепенное** (ТЗ §10.4): `rate_factor` не
восстанавливается при истечении кулдауна, а растёт по шагу
`×recovery_step` (потолок 1.0) при каждом ПОЛНОМ скане
(`NoteSuccess`), который также сбрасывает лестницу strikes.

**План (что сканировать сейчас).** `Plan`: RecoverCooldowns → для
каждого `active` источника, у которого текущее время (в его поясе)
попадает в окно: вес, остаток бюджета текущего часа
(`ScansThisHour` — все прогоны в текущем часовом слоте, включая
`running`: бегущий скан уже расходует запросы) → `nextSearchConfig`
(round-robin: активная конфигурация с самым старым последним сканом) →
сортировка по весу по убыванию. Потолок исчерпан (остаток ≤ 0) —
источник в плане не участвует.

### 2. Интеграция в сканер (`internal/scan/runner.go`)

`NewRunner(pool, dedupe, sched)` — третий аргумент; `Sched = nil` —
режим без расписания (тесты). В начале `Run`: источник не `active` или
в кулдауне → отказ со ссылкой на причину (до создания `scan_run`).
После завершения скана: captcha/`http_429` → `ApplyBackoff`;
`completeness='complete'` → `RecordYield` + `NoteSuccess`. Сбой
расписания не переворачивает уже завершённый скан (данные в БД) —
предупреждение в лог (ТЗ §0.4).

`cmd/pb/scan.go` — вынесен общий `runScanOnce(ctx, cfg, pool, sourceID,
configID)` (коннектор + скан + delist-пасс после полного скана):
`pb scan` и `pb schedule run` используют одно ядро.

### 3. Миграция `0020_schedule_backoff.sql`

`sources.cooldown_strikes INTEGER NOT NULL DEFAULT 0`,
`sources.rate_factor NUMERIC(4,3) NOT NULL DEFAULT 1.0 CHECK (>0)`.
Таблицы `scan_windows` / `scan_yield` — миграция 0014 (схема ТЗ §12,
этап 1); столбец `weight` — вычисляемый, хранит результат последнего
расчёта для аудита (ТЗ §10.2: «weight вычисляемый, не назначаемый»).

### 5. CLI — `pb schedule` (cmd/pb/schedule.go)

- `pb schedule show` — состояние: источники (state/strikes/
  rate_factor/кулдаун), warming_up, окна с весами и выходом
  («нет данных» ≠ «выход 0»), для текущего окна — потолок/в этом
  часе/остаток.
- `pb schedule run [-dry]` — **cron-точка** (ТЗ §3.4:
  самодостаточная пакетная задача): один вызов — один скан по плану
  (или ничего — не время окна / исчерпан потолок). `-dry` — показать
  выбор без запуска.
- `pb schedule init-windows -source ID [-timezone TZ] [-dow 0-6]
  [-hours 0-24] [-max N]` — создание окон (решение оператора: допустимое
  время и жёсткий потолок, ТЗ §10.2/§10.4). Пересечение окон одного дня
  недели — ошибка (плотность запросов была бы неопределённой).

### 6. Гонка live-тестов между пакетами — `internal/db/livelock.go`

`go test ./...` запускает бинари тестов **пакетов параллельно** на ОДНОЙ
тестовой БД (PB_TEST_DSN). Уязвимость: `zones.Assign` считает ВЕСЬ
`objects` (глобальная операция), и её live-тест фиксировал глобальное
базовое число `NoGeom`, ожидая `base+1`; параллельные пакеты
(scan/valuation/liquidity) между замером и присвоением вставляли/удаляли
объекты без геометрии — счётчик уходил, тест падал
(`NoGeom: 7783` вместо `7784`). Гонка усилена появлением четырёх новых
schedule live-тестов.

Исправление структурное, не ослаблением ассертов: **advisory lock**
`pg_advisory_lock(0x50424c495645)` на закреплённом соединении пула —
все live-тесты всех пакетов теперь сериализуются. Лок
session-scoped: соединение удерживается до конца теста (возврат в пул
отпустило бы лок рано), при гибели процесса Postgres освобождает лок
сам — вечной блокировки нет. Патч — во всех 7 открывателях пулов
live-тестов (zones, scan×3, valuation, liquidity, fx): `t.Cleanup`
LIFO — чистка данных под локом, лок отпущен последним. Проверено:
`go vet` + три полных прогона `go test -count=1 ./...` подряд —
стабильно зелёно.

## Не реализовано и почему

- **Периодический запуск (cron/systemd-timer).** `pb schedule run` —
  cron-точка: самодостаточная пакетная задача, делает один скан или
  ничего (ТЗ §3.4). Сам демон планирования — часть развёртывания на
  vzu5-omi (этапы 12–13); в ТЗ §10 демон не предписан.
- **Бэкап-канал при недоступности основного.** ТЗ §10 его не требует;
  источник один (bazos-reality), окон у IT/NL нет (источников нет).
- **Адаптация под robots.txt/Crawl-delay автоматически.** §10.1 требует
  только ЗАФИКСИРОВАТЬ проверку в `sources.access_policy` — сделано на
  этапе 3 (2026-08-27: robots.txt, ToS, отсутствие официального API).
  Автоматическое изменение потолка по robots.txt — не требование ТЗ.

## Допущения (ТЗ §0.2)

1. **В статистику выхода попадают только полные сканы.**
   Partial/failed не дают информации о числе новых объявлений (та же
   логика, что в delisted-логике, ТЗ §8.2); засчитать их как «0 новых»
   нечестно — это занижало бы слот. Полный скан с нулём новых —
   достоверная точка «в этот час новых не было» и записывается.
2. `min_obs_for_tuning = 14` полных сканов — операционная
   интерпретация «первых нескольких недель» (ТЗ §10.5); при 1 скане в
   день это ~2 недели.
3. `ma_window_days = 14` — две недели наблюдений на слот.
4. `ε = 0.10` — 10% бюджета всегда на исследование (ТЗ §10.3 долю
   задаёт конфигом, значение не предписано).
5. Бэкофф 60 мин ×2, потолок 72 часа; rate_factor: /2 на срыв, пол
   0.25, восстановление ×1.5 за полный скан — значения оператора (ТЗ
   §10.4 требует механику, не числа).
6. **Слот = время НАЧАЛА скана** в поясе страны (не середина, не
   завершения): момент начала — детерминирован оператором/планом.
7. `EffectiveCap` округляет ВНИЗ: потолок — верхняя граница, которую
   адаптация не имеет права превысить (ТЗ §10.4).
8. Окна одного дня недели не пересекаются (запрещено init-windows);
   если бы пересекались — консервативно: вес макс., потолок мин.
   (Plan содержит защитную ветку.)
9. Истечение кулдауна возвращает `state='active'`, но rate_factor
   восстанавливается только по шагам — «восстановление постепенное»
   (ТЗ §10.4) относится к частоте, а не только к состоянию.
10. `ScansThisHour` считает все `scan_runs` источника в текущем
    часовом слоте, включая `running`: запросы расходуются с момента
    начала.
11. Ручные состояния `disabled`/`blocked` (оператор) `RecoverCooldowns`
    не трогает — автоматика не отменяет оператора.

## Заглушки

Нет. Все функции рабочие: `Plan` выполняет реальные сканы через
`runScanOnce`; бэкофф/выход пишутся в реальные таблицы. Единственное
ограничение — внешнее: нет cron-демона (см. «Не реализовано»).

## Особенности окружения

- Сервер в UTC; окна и слоты — в поясе страны (Europe/Prague = UTC+2
  летом). Реальный скан 02:25 UTC = 04:25 CEST → слот `1-4`.
- Live-тесты всех пакетов сериализованы advisory-локом
  (`internal/db/livelock.go`) — см. раздел 6 «Реализовано».
- Песочные страны/источники по пакетам (пакеты гонятся параллельно):
  scan = CZ `pb-scan-test`, schedule = CZ `pb-sched-*`, delist = DD,
  valuation = VV, liquidity = LL, zones = tt.

## Требует ручной проверки

1. **Бэкофф на реальной капче/429 от reality.bazos.cz.** Механика
   покрыта live-тестом на синтетической капче; реальный блок площадки
   не форсировался (ТЗ §13 — обход технических мер защиты не
   применяется) и к 2026-08-31 не встречался (всё время `active`,
   strikes=0).
2. **Выход из warming_up на реальных данных.** Порог 14 полных сканов
   накопится при ежедневном сканировании ~2 недели (первая реальная
   точка scan_yield — 2026-08-31). До этого веса равны — это честное
   состояние, а не дефект (ТЗ §10.5).
3. **Периодический вызов `pb schedule run`** — на этапе 12–13
   (развёртывание на vzu5-omi): интервал вызова должен быть ≤ 1 часа
   (потолок считается на часовой слот).

# Отчёт этапа 6 — Логика delisted + защиты (ТЗ §8.2)

Дата: 2026-08-28. Команда: `pb delist` прогнана на реальных данных (см. «Результаты на реальных данных»).

## Реализовано

### 1. Delist-пасс (ТЗ §8.2) — `internal/scan/delist.go`

`RunDelistPass(ctx, pool, cfg, sourceID) (*DelistReport, error)` — маркировка объектов
`delisted` по одному источнику. «Исчезновение из выдачи не является продажей» (ТЗ §8.2):
статус присваивается только по правилам ниже, со всеми четырьмя защитами.

**Как считаются промахи (без таблицы состояния).** Последовательные промахи выводятся
из неизменяемой истории (`scan_runs` + `raw_listings` + `object_listings`), отдельной
таблицы-счётчика нет:

- «Объект найден в прогоне R» = существует строка `raw_listings` (R, источник,
  external_id), где external_id принадлежит объекту через `object_listings`.
  По `object_listings.raw_listing_id` смотреть нельзя: он указывает на **первое**
  matched-объявление, а последующие сканы создают новые `raw_listings` на тот же
  (object, source, external_id).
- Счёт промахов идёт по «домашней» конфигурации поиска объекта — конфигурации
  последнего **полного** прогона, где объект найден; если нигде не найден —
  конфигурации первой записи; если и того и другого нет — объект пропускается
  (безопасно: delisted не присваивается). У источника с несколькими конфигурациями
  отсутствие объекта в выдаче чужой конфигурации промахом не считается.
- Прогон считается «после» последней находки по `scan_runs.started_at`.

**Четыре защиты ТЗ §8.2:**

| № | Защита | Реализация |
|---|---|---|
| 1 | Только полные сканы | `missQuery` считает только `completeness = 'complete'`; `pb scan` вступает в pass только после complete-прогона |
| 2 | N последовательных промахов, N ≥ 2 | `misses >= min_consecutive_misses`; конфиг валидируется `>= 2` |
| 3 | Массовое исчезновение = аномалия | Если доля кандидатов > `max_delisted_share_pct` % — прогон остановлен: **изменения ни к одному объекту не применяются**, запись в `notifications` (kind `delist_anomaly`, recipient `operator`, статус `pending` — доставит бот этапа 8) |
| 4 | URL-чек объявления | Если источник разрешает (`sources.url_check_allowed`): 404/410 → исчезновение подтверждено; 2xx по тому же URL → объект остаётся active; редирект на другое объявление того же домена → причина `relisted`; 403/429/5xx/сеть/редирект вне домена → решения нет, объект остаётся active (честный счётчик `url_failed`) |

Порядок важности: №3 проверяется **до** URL-чеков — при катастрофе не тратим HTTP-запросы.
Применение — одна транзакция на всех кандидатов, `WHERE status='active'` — защита от
гонки с параллельным сканом.

**Причины (автоматика).** Присваиваются только `unknown` и `relisted`. `sold`
автоматикой **не присваивается никогда** (ТЗ §8.2: подтверждает только кадастровый
источник, их в системе нет). `withdrawn_by_owner` и `scan_gap` зарезервированы за
оператором (ручная разметка).

**Обратимость.** В `internal/scan/match.go` (ветка `source_external`): delisted-объект,
найденный снова под тем же (source, external_id), возвращается в `active`
(`delisted_reason`/`delisted_at` очищаются). Без этого delisted-объект, найденный
снова, получал бы обновления цены/даты, но остался бы delisted навсегда.

### 2. Конфиг — блок `delist:`

| Ключ | Значение | Валидация |
|---|---|---|
| `min_consecutive_misses` | 2 | `>= 2` (ТЗ: «минимум 2») |
| `max_delisted_share_pct` | 25 (допущение исполнителя) | `(0, 100]` |
| `url_check_timeout_sec` | 10 | `>= 1` |

Блок обязателен: отсутствует/некорректный → `config.Load` падает (fail-fast, как и все
остальные блоки). Пример — `config/config.example.yaml`, в `config/config.yaml` блок
добавлен.

### 3. Миграция 0018

`migrations/0018_delist.sql`: `sources.url_check_allowed BOOLEAN NOT NULL DEFAULT FALSE`
(новый источник без явного разрешения URL-чеков — без них) + `TRUE` для `bazos-reality`
(страницы объявлений Bazoš публичные, чек не нарушает access_policy).

### 4. Команды

- `pb delist [-source ID]` — pass по всем источникам с привязанными объектами (по
  умолчанию) или по одному. Журнал: `delist: source=… active=… candidates=…
  delisted=… url_alive=… url_failed=…`, при аномалии — «АНОМАЛИЯ (ТЗ §8.2)… изменения
  не применены, записано уведомление оператору».
- `pb scan` — после **полного** скана автоматически выполняет delist-пасс по тому же
  источнику (неполные прогоны не вступают в pass — защита №1).

### 5. Тесты

- Live (env `PB_TEST_DSN`, источники-заглушки `pb-del-test`/`pb-del-url-test`, страна
  «TT», cleanup через t.Cleanup), 5 — по одной на каждую защиту/свойство:
  - `TestDelistIncompleteScansNotCounted` — №1: partial/failed прогоны (http_429,
    network) в промах не идут, объект после 2 неполных + 1 полного промаха остаётся
    active.
  - `TestDelistConsecutiveMissesRequired` — №2: 1 промах — не delisted; 2
    последовательных — delisted/`unknown`; третий прогон идемпотентен (кандидатов нет).
  - `TestDelistMassAnomalyStopsPass` — №3, **критерий готовности ТЗ** («симуляция
    сбоя источника не приводит к массовой смене статусов»): 20/20 объектов исчезли из
    полных сканов → `Anomaly=true`, `Delisted=0`, все 20 остаются active, запись
    `notifications` (recipient `operator`, share_pct=100).
  - `TestDelistURLCheck` — №4: httptest-сервер; A (200 по тому же URL) → active,
    B (404) → delisted/`unknown`, C (302 → другое объявление того же домена) →
    delisted/`relisted`.
  - `TestDelistReactivateOnReturn` — обратимость: после delisted объект возвращается
    через **настоящий** `scan.Runner` (fakeConn) — статус `active`, причины очищены.
- Юнит (без БД): `internal/config/config_test.go` — `TestLoadDelistValidation`, 6
  кейсов (корректный блок; misses=1; share=0; share=101; timeout=0; блок отсутствует).
- `go build ./... && go vet ./...` — чисто; `gofmt -l` на новых файлах — чисто.

## Результаты на реальных данных (2026-08-28, `pb delist`)

```
delist: source=bazos-reality active=7762 candidates=0 delisted=0 url_alive=0 url_failed=0
```

Честный no-op, и именно так должно быть: у источника ровно **один** полный скан
(2026-08-27), в котором найдены все 7762 объектов → у каждого `misses=0` < 2. Делист
возможен не раньше второго полного скана, в котором объекты не найдены.
Сверка в БД после прогона: `active=7762, delisted=0` — изменений нет.
Миграция 0018 применена: `bazos-reality.url_check_allowed = t`.

## Не реализовано и почему

- **Доставка уведомления об аномалии** — запись в `notifications` сделана
  (kind `delist_anomaly`), доставку исполнит Telegram-бот этапа 8 (общая очередь).
- **Автоматическое расписание pass** — pass вшит в `pb scan` (после complete) и доступен
  вручную через `pb delist`; адаптивное расписание — этап 11.
- **`sold` / `withdrawn_by_owner` / `scan_gap`** — автоматикой не присваиваются
  (см. выше); это поведение, предписанное ТЗ §8.2, а не отсутствие функциональности.

## Допущения

- `max_delisted_share_pct: 25` — число исполнительское (ТЗ требует защиту с порогом из
  конфига, но значения не задаёт). 25% — компромисс: ниже — ложные срабатывания на
  обычном обороте рынка, выше — поздняя реакция на сбой.
- Порог №3 считается по **кандидатам** (до URL-чеков) — это надмножество фактических
  делистов, т.е. защита срабатывает консервативно (чаще, чем нужно, но не позже).
- Редирект на «похожее объявление» (ТЗ §8.2) формализован как редирект на **другой
  путь того же хоста**: URL объявления содержит уникальный идентификатор, сравнение
  host+path достаточнее и не требует парсинга страницы.
- Повторная публикация того же объекта под **новым** external_id создаст новый объект
  (кросс-сорсинговая дедупликация видит только active-объекты; старый, если он delisted,
  в совпадение не попадёт). Вероятность низка (площадки не переиспользуют id),
  документировано для этапа с кадастровыми источниками.
- URL-чек последовательный, с вежливой паузой сканера (`scan.page_delay_ms`); явного
  лимита на число чеков за прогон нет — при доле ниже порога кандидатов ограниченно
  (≤ порога × active).
- `pb scan` с complete-прогоном теперь всегда включает delist-пасс — время скана
  вырастает на число URL-чеков (в текущих данных — 0).

## Требует ручной проверки

1. Второй полный скан `bazos-reality` (после `pb scan -source bazos-reality
   -search-config 11`): delist-пасс вступит в силу; если площадка честно сняла
   объявления, они получат `delisted/unknown` (URL-чек разрешён), а не «продажу».
2. Повторный запуск `pb delist` сразу после первого — идемпотентен (active только
   уменьшится, кандидатов 0).
3. Путь аномалии покрывается live-тестом `TestDelistMassAnomalyStopsPass` (смена
   вёрстки: все объекты исчезают из двух полных сканов → ноль изменений + уведомление).
   На реальных данных воспроизвести штатно нельзя (объекты в выдаче есть).
4. Уведомление об аномалии увидит оператор после этапа 8 (сейчас — строка в
   `notifications`, статус `pending`).

# Отчёт этапа 10 — Асинхронный переводчик описаний (ТЗ §11)

Дата: 2026-09-02. Команды: `pb translate run [--limit N] [--country XX]`,
`pb translate status`. Критерий этапа (таблица ТЗ): «Переводы в БД,
идемпотентны по хешу».

## Реализовано

### 1. Пакет `internal/translate/` — движок переводов (ТЗ §11)

| Файл | Содержимое |
|---|---|
| `llm.go` | `Client` — OpenAI-совместимый API (`POST {base_url}/chat/completions`), `Result` (текст, модель, токены), `ErrPermanent` (4xx), `ErrRateLimit` (429 + пауза) |
| `detect.go` | `Detector` — язык оригинала по тексту: кириллица → `ru`; латиница — маркеры + профиль частот букв (en/it/nl/cs) |
| `translate.go` | `Run` — прогон (cron-точка), `Status` — сводка конвейера, `HashDescription` (sha256 hex), `Targets` (целевые языки) |

**Идемпотентность (ТЗ §11).** Ключ перевода — `sha256(description_original)`,
сравнивается **на стороне SQL** (`pgcrypto.digest`, миграция 0022): выборка
кандидатов не тянет все объекты, а перевод того же текста с другого объекта
переиспользуется без обращения к LLM (индекс `translations_hash_idx` из
0012). Совпадение хеша Go (`crypto/sha256`) и SQL (`digest`) проверено на
реальной БД (одинаковый хеш для 'test').

**Выборка кандидатов.** Объект кандидат, если описание непусто,
`length <= max_chars` (слишком длинные не отправляются в LLM — ТЗ §11 — и не
занимают лимит прогона) и нет **свежих** строк для нужных языков. Свежая —
с хешем ТЕКУЩЕГО текста (описание изменилось — прежние переводы устарели и
удаляются в начале обработки объекта: показать старый текст как текущий —
подстановка). Сколько языков нужно — по `language_original`: оригинал на
ru/en требует один (другой) язык, прочие — оба. Фильтр `--country` —
управление стоимостью LLM по рынкам (cron-точки по странам).

**Политика ошибок (ТЗ §11: «если перевод не получен — поле остаётся
NULL»).** Ошибка LLM (5xx, сеть, пустой ответ) — объект не переведён,
строка не пишется, прогон продолжается (`failed++`, повторит следующий
cron). 429 — пауза `Retry-After` (дефолт 3 c, потолок 60 c) и повтор; при
исчерпании попыток — мягкий останов прогона **без ошибки** (дальше тот же
лимит), продолжит следующий cron. Прочие 4xx (неверный ключ) —
`ErrPermanent`: прогон останавливается с явной ошибкой (дальше — та же
ошибка). Пустой перевод не сохраняется (псевдоперевод запрещён).

**Каждый перевод хранит `model`, `translated_at`, `token_cost` (ТЗ §11).**
Модель — реально обслуживавшая запрос (из ответа API, fallback —
запрошенная); `token_cost` — `total_tokens` (fallback `prompt+completion`),
0 (нет usage в ответе) — NULL: стоимость неизвестна, а не нулевая.

**«Вычисляются при сохранении» + «асинхронно и вне критического пути».**
Реализовано как pending-очередь + самовосстанавливающийся cron-прогон
(тот же паттерн, что очередь уведомлений, этап 8): скан не ждёт LLM,
дедупликация/оценка/уведомления на перевод не зависят; прогон доводит
очередь до нуля, частичный прогон — нормальный исход.

### 2. Детектор языка оригинала (ТЗ §11: «не по стране»)

Сканер кладет `language_original` константой источника (bazos — `cs`);
переводчик уточняет по тексту:

1. Кириллица ≥ 50% букв → `ru` (детерминированно).
2. Латиница: сильные маркеры (почти исключительные буквы/граммемы: cs
   řťňěůď, it zione/amento/imento, nl ë/ij/appartement, en the/ing/tion —
   2 очка) + слабые (1 очко) + 0,3× Szymkiewicz–Simpson-наложение профиля
   частот букв на стандартные распределения (открытые лингвистические
   данные). Уверенность = доля выигрыша лучшего языка над вторым.

Честная неопределённость: текст короче 20 букв или уверенность < 0,35 —
`language_original` **не переопределяется** (константа коннектора
остаётся, гадать вместо определения не будем). Проверено: немецкий текст
(не в целевом наборе) даёт уверенность ~0,13 < порога — не угадывается.

### 3. API (internal/api/objects.go)

`objectOut` расширен: `description_original`, `language_original`,
`translation_ru` / `translation_en` (`text`, `model`, `token_cost`,
`translated_at`). Чтение — из БД, без обращения к LLM (ТЗ §11): два
`LEFT JOIN LATERAL` с фильтром свежести `source_hash =
encode(digest(description_original,'sha256'),'hex')` — устаревший перевод
(описание изменилось, прогон ещё не прошёл) читается как **NULL** («перевод
недоступен»), а не как текущий.

### 4. Конфиг — блок `translate:` (опциональный)

```yaml
translate:
  api_key: ""            # пусто — переводчик не настроен
  base_url: "https://api.openai.com/v1"
  model: ""
  timeout_sec: 60        # <= 0 — дефолт 60
  max_chars: 4000        # <= 0 — дефолт 4000; < 100 — ошибка загрузки
```

Без `api_key` конфиг валиден, но `pb translate run` — явная ошибка с
инструкцией (ТЗ §0.4: не заглушка, а понятная инструкция); переводы
остаются NULL. `api_key` без `model` — ошибка на загрузке (конфиг, который
не может работать). `config.example.yaml` + локальный `config.yaml`
обновлены.

### 5. Миграция `0022_pgcrypto.sql`

`CREATE EXTENSION IF NOT EXISTS pgcrypto` — sha256 для идемпотентности на
стороне SQL. Таблица `object_translations` и индекс по `source_hash` — из
0012 (этап 2), без изменений.

### 6. CLI — `pb translate` (cmd/pb/translate.go)

- `pb translate run [--limit N] [--country XX]` — cron-точка: перевести
  недостающие/устаревшие ru/en; `--limit` — сколько объектов за прогон
  (дефолт — довести очередь до нуля), `--country` — один рынок.
- `pb translate status` — состояние конвейера: объектов с описанием, со
  свежим переводом, pending, слишком длинных, строк по языкам, моделей,
  последний перевод; работает без api_key (читает только БД), без ключа —
  явная пометка «переводчик НЕ настроен».

**Исправление CLI, найденное при смоук-тесте этапа.** Документированный флаг
`pb <субкоманда> [--config PATH]` молча игнорировался: `flag.Parse()` в Go
останавливается на первом позиционном аргументе (субкоманде), поэтому глобальный
`--config` после неё не парсился — бинарь всегда читал дефолтный
`config/config.yaml` (рабочей альтернативой был только `$PB_CONFIG`). Тихо
игнорируемый флаг — ровно то, что запрещает ТЗ §0.4. Исправлено в
`cmd/pb/main.go`: субкоманда берётся как `flag.Arg(0)`, флаги субкоманды —
`flag.Args()[1:]`, порядок — `pb [--config PATH] <субкоманда> [флаги]`; usage
перезаписан под фактический контракт. Проверено смоук-тестом:
`pb --config <временный конфиг со своим портом> serve` слушает именно порт из
конфига, а не дефолт.

**Исправление заранее существовавшего флейка в `internal/liquidity`**
(поймано при прогоне тестовых пакетов этапа; код этапа 10 не относится).
`TestRunLiveTrainPredict` периодически падал: `status = "uncalibrated",
reject = "fit_not_converged"` (замечено 2026-09-02; тот же сбой воспроизведён
на чистом worktree HEAD без изменений этапа — не регрессия). Причина: признак
`month_*` — календарный месяц начала интервала (ТЗ §9.2), а даты синтетического
сценария относительны к текущему времени (`liqDaysAgo`) — состав
design-матрицы зависит от дня запуска, а на недоопределённом сценарии
(8 событий / ~30 параметров — граница квазисепарации) IRLS сходится лишь на
части дат (проба с полностью зафиксированными часами: 2 из 8 дат, при
идентичных periods/train/test/events). Исправление: в `run.go` вынесен
`nowUTC` — источник «сейчас» прогона (конец активных объектов, cutoff
временного разбиения, версия модели; по умолчанию `time.Now().UTC()`,
поведение продакшена не изменено); тест фиксирует оба часа на
`liqTestNow = 2026-09-01 12:00 UTC` (`pinLiqNow(t)`, восстановление в
Cleanup). Тест теперь детерминирован и проверяет механику: временное
разбиение, обучение на событиях до T, публикацию, прогнозы. Код продакшена
не тронут: несходимость фида остаётся отказом по правилам ТЗ §9
(`uncalibrated` / `fit_not_converged` — недоопределённая модель не
публикуется). Файлы: `internal/liquidity/run.go`, `internal/liquidity/
liquidity_test.go` — отдельный коммит перед коммитом этапа.

## Не реализовано и почему

- **Автоверификация качества перевода** — заявленное ограничение ТЗ §11
  («качество перевода автоматически не верифицируется — это заявленное
  ограничение, а не скрытое»).
- **Отображение описания в дашборде.** Дашборд (этап 2) не рендерит
  описания объектов вовсе (ни оригинала) — это существующая граница
  дашборда v1. Требование ТЗ §11 «чтение в UI идёт из БД, без обращения к
  LLM» выполнено на уровне API: `description_original`,
  `language_original`, `translation_ru/en` отдаются из `object_translations`
  с фильтром свежести по хешу. Блок описания в дашборде (при добавлении)
  читает эти поля.

## Допущения (ТЗ §0.2)

- **Самодостаточный детектор языка**, а не библиотека (golang.org/x/text
  v0.29.0 не содержит language/detect — проверено в zip): прозрачный
  статистический метод (маркеры + профили частот букв) без подгонки под
  тестовые выборки. Методологические константы классификатора (не
  операционные пороги): `minDetectLetters = 20` (короче — по чему судить),
  `detectConfThreshold = 0.35` (разделяет чёткий сигнал и шум).
- **`max_chars = 4000`** — дефолт лимита длины описания для LLM (операционный
  параметр в конфиге, ТЗ §0.1: стоимость перевода растёт с длиной).
- **«При сохранении» = асинхронно после сохранения**: pending-очередь +
  cron-прогон (паттерн очереди уведомлений, этап 8) — скан и остальной
  критический путь не ждут LLM (ТЗ §11: «вне критического пути»).
- **`--country`** — операционный фильтр прогона: стоимость LLM по рынкам
  управляется отдельно (cron-точки по странам).
- **Слишком длинные описания** (length > max_chars) переводчиком не
  берутся (не отправляются в LLM) и показываются отдельно в `status`
  (`too_long`) — это не зависание очереди, а лимит.

## Заглушки

Нет. Без api_key `pb translate run` — явная ошибка с инструкцией, а не
тихий no-op (ТЗ §0.4); переводы NULL, UI-слой (API) отдаёт NULL → «перевод
недоступен».

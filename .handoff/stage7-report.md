# Отчёт этапа 7 — Модель ликвидности на person-period данных (ТЗ §9)

Дата: 2026-08-29. Команда: `pb liquidity` (см. «Результаты на реальных данных»).

## Реализовано

### 1. Пакет `internal/liquidity/` — дискретная модель дожития (ТЗ §9.2)

Модель: **пуллогированная логистическая регрессия на недельных
person-period строках** (дискретная модель дожития). Наблюдение объекта
разбивается на недельные интервалы от начала экспозиции до `delisted_at`
(или до текущего момента, если объект активен). Активные объекты дают
только нули и остаются в выборке — это и есть корректный учёт правого
цензурирования (ТЗ §9.1). Целевая 1 попадает ровно в один интервал: тот,
в котором лежит `delisted_at`.

**Файлы:**

| Файл | Содержимое |
|---|---|
| `dataset.go` | Person-period выборка: недельная дискретизация (`objIntervals`), предикторы цены на начало интервала (`priceFeaturesAt`), `valDevAt` |
| `model.go` | Раскладка колонок (`colLayout`), кодирование (`encode`), логистическая регрессия IRLS/Ньютон (`fitLogistic`), прогноз за горизонт (`horizonProb`) |
| `metrics.go` | Калибровочные децили (`CalibrationDeciles`, `MaxCalibDev`), разложение Brier (`BrierDecompose`), C-index (`CIndex`) |
| `run.go` | `Run` — прогон: гейт min_events → выборка → временное разбиение → фит → валидация → запись |
| `save.go` | Запись строки модели + прогнозов (пачками по 100, `ON CONFLICT`) |
| `liquidity_test.go` | 8 unit-тестов + 2 live-теста (PB_TEST_DSN) |

**Раскладка признаков** (ТЗ §9.2: «сплайн или набор индикаторов
интервалов»; с текущим объёмом событий сплайн переобучил бы — набор
индикаторов честнее):

```
[intercept | week_0..11, week_12plus | month_2..12 (январь — база) |
 price_reductions, price_drop_pct, days_since_price_change,
 price_increased, price_deviation | zone_* | attr_* (реестр)]
```

~30 параметров при нулевых зонах/атрибутах.

**Защита от утечки будущего** (ТЗ §9.2): изменяющиеся во времени
предикторы цены берутся **только по строкам `price_history` с
`change_at <= t`**, где t — начало интервала. Подстановка финальной цены
в ранние интервалы — утечка целевой переменной из будущего, запрещена.
На старте экспозиции значения естественно нулевые (0/0/0/0).

**Прогноз за горизонт** (ТЗ §9.2): `P(T) = 1 − ∏(1 − h_k)` по первым
`ceil(T/7)` неделям; недельные предикторы (week/month) сдвигаются по
шагам, предикторы цены заморожены на текущих значениях — будущее
поведение цены неизвестно (допущение, см. ниже).

**Логистическая регрессия (IRLS/Ньютон)**: матрица весов n×n
**не материализуется** (на реальных данных это сотни МБ, ТЗ §3.8) —
XᵀWX и правая часть накапливаются напрямую за O(n·K²). Крошечный L2
(1e-6) на неконстантных столбцах — защита от полной сепарации и
вырожденных (постоянно нулевых) колонок; числовое сжатие коэффициентов
~1e-5 — стандарт, а не модельное допущение. Несходимость (200 итераций,
tol 1e-9) → статус `uncalibrated`, причина `fit_not_converged`.

### 2. Прогон `Run` — порядок и гейты

```
гейт min_events (ТЗ §9.3) → реестр атрибутов → выборка (только если гейт
пройден) → временное разбиение (ТЗ §9.4) → фит → валидация на хольдауте
→ калибровочный гейт (ТЗ §9.4) → запись модели + прогнозов (одна
транзакция, ТЗ §3.4)
```

- **Гейт min_events** (ТЗ §9.3): завершённые наблюдения — объекты со
  статусом `delisted` и `posted_date_unreliable = FALSE` (ненадёжный
  старт исключён из обучения, ТЗ §14.5.1). Дешёвый подсчёт ДО построения
  выборки: полная выборка строится только если гейт пройден. Ниже порога
  → статус `insufficient_history`, прогнозы NULL с причиной
  (холодный старт, ТЗ §14.5 — нормальное состояние, а не сбой).
- **Начало экспозиции** (ТЗ §14.5.1): `min(first_seen_at, min posted_at)`
  по всем сырым наблюдениям объекта. `posted_at` площадки ненадёжен
  (обновляется при редактировании) — минимум по истории восстанавливает
  изначальную дату как это возможно.
- **Временное разбиение** (ТЗ §9.4, случайное запрещено):
  `T = minStart + holdout_ratio × (maxEnd − minStart)` по окну
  наблюдений. Интервалы с `End ≤ T` — обучение, после — проверка.
  Зоны — только из обучающих строк: тест/прогноз видят тот же набор
  индикаторов (новые зоны — все нули).
- **Отказы до публикации** (статус `uncalibrated`, прогноз NULL с
  причиной `calibration_failed`, оповещения не отправляются — ТЗ §9.4):
  - `no_events_in_train` — все уходы после T;
  - `test_too_small` — проверочных интервалов < `minTestIntervals` (20,
    допущение исполнителя);
  - `fit_not_converged`;
  - `calibration_too_few_deciles` — непустых децилей < 2 (допущение
    исполнителя);
  - `calibration_failed` — max |predicted − actual| по децилям >
    `max_calib_dev`.
- **Валидация** (ТЗ §9.4): калибровочная кривая по децилям
  предсказанной вероятности, Brier score (+ разложение
  reliability/resolution/uncertainty), C-index — **все сохраняются в
  строку версии модели** (выводятся в дашборде).

**Прогнозы** (все объекты страны/типа сделки):
- `delisted` → NULL с причиной `delisted` (объект уже ушёл с рынка,
  прогноз не имеет смысла, ТЗ §9.3) — независимо от статуса модели;
- `active` → вероятность в [0,1] (published) или NULL с причиной
  `insufficient_history` / `calibration_failed`.

### 3. Миграция `0019_liquidity.sql` — `liquidity_models`

Таблица **историческая**: каждый прогон добавляет строку (метрики
валидации хранятся вместе с версией модели, ТЗ §9.4); читается только
последняя по `computed_at`. Ключевые колонки: `status`
(published/uncalibrated/insufficient_history), `reject_reason`,
`n_completed_events`, `n_person_periods`, `n_params`, `train_cutoff_at`,
`n_train`/`n_test`, `calibration` JSONB, `max_calib_dev`, `brier_score`,
`brier_decomp` JSONB, `c_index`, `params` JSONB (коэффициенты для
аудита). Прогнозы — в существующей `liquidity_estimates` (миграция
0013, одна строка на (object, horizon), перезаписывается прогоном).

Запись строки модели и всех прогнозов — **в одной транзакции**
(ТЗ §3.4): сбой обучения не оставляет «наполовину» состояний.

`cmd/pb/liquidity.go`: по умолчанию — все страны/типы сделок из

### 6. API

- **`GET /api/liquidity?country=XX&deal_type=T`** (`internal/api/liquidity.go`):
  последняя версия модели (по `computed_at`). Параметры опциональны;
  валидация: country — 2 буквы, deal_type — из `dashboard.deal_types`.
  Холодный старт (прогонов не было) → `200 {"model": null}` (ТЗ §14.5).
- **`GET /api/objects`** — добавлено поле `hazard`
  (`internal/api/objects.go`): последние по `computed_at` строки
  `liquidity_estimates` (LATERAL-джойн), `null` у объекта без прогона.
  Поля: `horizon_days`, `probability` (NULL до публикации), `null_reason`,
  `model_version`, `events_in_training`, `computed_at`.

### 7. Дашборд

- **Вкладка «Ликвидность»** (`LiquidityView.tsx`): фильтры
  страна/тип сделки; статус модели (published / не опубликована: порог
  калибровки / мало истории) + причина; сводка (рынок, версия, время
  прогона, горизонт, завершённые наблюдения против порога,
  person-period строк, параметры, разрез T, train/test,
  max_calib_dev, Brier, C-index); разложение Brier; **калибровочная
  кривая** (SVG, без графических библиотек: децили предсказанной
  вероятности против фактической доли ушедших, диагональ — идеальная
  калибровка); примечание «модель предсказывает уход с рынка, не
  продажу» (ТЗ §9.3).
- **Вкладка «Объекты»**: колонка «Вероятность ухода» (после оценки):
  процент за горизонт с тултипом (горизонт, версия модели, событий в
  обучении); до публикации — причина (мало истории / калибровка не
  пройдена / ушёл с рынка).
- i18n ru/en: новые ключи `liquidity.*`, `objects.hazard*`,
  `app.tab_liquidity`.

## Тесты

**Unit (без DB), 8 шт.** (`internal/liquidity/liquidity_test.go`):

| Тест | Проверяет |
|---|---|
| `TestObjIntervalsTargets` | Целевая 1 ровно в одном интервале (границы: уход на 7-й день — первый интервал), активные — только нули, последний интервал доведен до End |
| `TestPriceFeaturesAtNoLeakage` | Предикторы цены используют только `change_at <= t`: до первой цены — 0/0/0/0, будущие снижения не видны |
| `TestValDevAt` | Последняя `price_deviation` на момент t, иначе nil |
| `TestFitLogisticRecoversSignal` | IRLS восстанавливает известные β (4000 строк, tol 0.25) |
| `TestBrierDecompose` | Tождество Brier = reliability + resolution + uncertainty + (внутренние члены) на 3 выборках, включая «калиброванную двухблочную» (reliability → 0) |
| `TestCIndex` | Perfect 1.0, реверс 0.0, все связки 0.5, смешанный 0.5, без событий — comparable 0 |
| `TestCalibrationDeciles` | n=20 → 10 сбалансированных децилей, предсказанные доли неубывающи |
| `TestHorizonProb` | `1 − ∏(1−h_k)` по шагам со сдвигом недель |

Тесты поймали 3 реальных бага на этапе разработки (исправлены):
целочисленное деление `Duration/Duration` при дискретизации; неверная
ирландская итерация IRLS (взвешенная правая часть имела фиксированную
точку β=0 — заменена на правильный Ньютон `(XᵀWX)β' = XᵀWX·β + Xᵀ(y−p)`);
счёт concordant-пар в C-index (нули с предсказанием НИЖЕ, а не выше).

**Live (PB_TEST_DSN), 2 шт.** — песочница-страна `LL` (отдельно от `TT`
этапов 4–6: пакеты гонятся параллельно):

| Тест | Сценарий |
|---|---|
| `TestRunLiveInsufficientHistory` | 3 delisted (< min_events=100) + 2 active → статус `insufficient_history`; строка модели с NULL метриками; все прогнозы NULL (3×`delisted`, 2×`insufficient_history`) |
| `TestRunLiveTrainPredict` | 10 delisted (старты 70..88 дн. назад, уходы 14..42 дн. после старта) + 30 active, holdout 0.5 → 8 уходов в обучающем окне, 2 — в проверочном, ≥20 интервалов в проверочном → published; метрики и параметры в строке модели; 30 активным вероятности в [0,1] с версией и events_in_training; 10 delisted — NULL `delisted` |

## Допущения исполнителя (ТЗ §0.2)

1. `min_events = 100` — нижняя граница осмысленного пулированного
   обучения при ~30 параметрах (ТЗ порог не задаёт).
2. `max_calib_dev = 0.10` — 10 процентных пунктов (ТЗ требует порог,
   значение не задаёт).
3. `holdout_ratio = 0.25`, `horizon_days = 30` — типовые значения;
   ТЗ задаёт горизонт как параметр модели, конкретное число не
   предписано.
4. `minTestIntervals = 20`, `minDeciles = 2` — минимумы, ниже которых
   метрики шум, а «максимальное отклонение калибровки» не имеет смысла.
5. Предикторы цены в `horizonProb` заморожены на текущих значениях
   (будущее поведение цены неизвестно); недельные/month-предикторы
   сдвигаются по шагам.
6. Недельная дискретизация (ТЗ §14.5.2: время ухода интервально
   цензурировано, «точность до дня» была бы ложной).
7. Модель предсказывает **уход с рынка, не продажу** (ТЗ §9.3) —
   отражено в UI («вероятность ухода»), в причинах NULL и в примечании
   дашборда.

# Отчёт по этапу 3 — реестр атрибутов, первый simple-коннектор, scan_runs с честным completeness (ТЗ §15.3)

Дата: 2026-08-27. Хост: `vzu5-claw`. Исполнитель: Claude (Claude Code).
Критерий готовности этапа: «Сквозной путь скан → raw_listings → objects;
неполный скан не влияет на статусы».

## Реализовано

### Реестр атрибутов (ТЗ §6)

- Миграция `0005_attribute_registry` (этап 1): `attribute_registry`
  (country CHAR(2), key, data_type ∈ bool/enum/int/float, allowed_values
  JSONB, used_in_pricing, label_ru/label_en, source_evidence,
  UNIQUE(country,key)).
- Наполнение для CZ (данные заданы пользователем в ТЗ §6 — «как данные»):
  - `ownership_type` enum ["osobni","druzstevni"];
  - `panel_renovation` enum ["original","revitalized"];
  - `has_gas` bool.
- `source_evidence` у каждой строки — реальное: для CZ значения из ТЗ §6;
  для `ownership_type` дополнительно подтверждено, что источник публикует
  поле «Vlastnictví» (объявление reality.bazos.cz, проверено 2026-08-27).
- IT/NL в реестре **не заполнялись** — по ТЗ §6 только по фактическому
  разбору агрегаторов этих стран, не «по памяти» (этапы 4+).
- Валидация фильтров по реестру уже работала на этапе 2
  (`POST/PUT /api/search-configs`): теперь реестр CZ не пуст, фильтры
  атрибутов отображаются в форме дашборда.

### Источник и access_policy (ТЗ §13)

- Источник `bazos-reality` (reality.bazos.cz, CZ, sale+rent, kind=simple,
  state=active) записан в `sources` **до написания коннектора**.
- `access_policy` (JSONB, проверено 2026-08-27):
  - **Официального API нет** — проверено; сайт раздаёт RSS
    (www.bazos.cz/rss.php?rub=re&cat=NN&typ=NN), но только последние
    объявления — для детектирования исчезновений (ТЗ §8.2.1) не подходит,
    поэтому коннектор читает HTML-страницы категорий с полной пагинацией.
  - **robots.txt** (оба хоста): страницы категорий `/prodam/…`,
    `/pronajmu/…` и объявления `/inzerat/…` разрешены для общего
    User-agent; запрещены URL-параметры поиска/сортировки/фильтров
    (`/*hledat=`, `/*cenaod=`, `/*cenado=`, `/*order=`, …) и сервисные
    .php; именованные боты (trovitBot, pricebot, magpie-crawler,
    SemrushBot, trendictionbot, BLEXBot, Riddler) — disallow.
  - **ToS** (www.bazos.cz/podminky.php): пункта о запрете
    автоматизированного доступа/скрапинга **не найдено** — условия
    регулируют содержание объявлений и GDPR (оператор — физ. лицо,
    IČO 65773551). Зафиксирован жизненный цикл: бесплатное объявление
    удаляется автоматически через 2 месяца — исходное замечание для
    delisted-логики «истёк срок на сайте» (этап 6).
  - `connector_rules`: описательный User-Agent, пауза между страницами
    (config `scan.page_delay_ms`), полная пагинация, обход технических
    мер защиты не применяется (ТЗ §13).
- `available_filters`: пусто — фильтры по URL запрещены robots.txt;
  коннектор честно отклоняет `min/max_price_minor` и `min/max_area_sqm`
  явной ошибкой.

### Коннектор reality.bazos.cz (первый simple-коннектор)

- `internal/connectors/bazos`: полный проход по всем страницам одной
  категории (deal_type × property_type), 20 карточек на страницу, число
  страниц — из счётчика «Zobrazeno 1-20 inzerátů z N» (окно ссылок
  пагинации на странице неполное — только ближайшие страницы, поэтому
  полный скан возможен только через счётчик).
- Поля карточки: external_id + URL объявления, дата публикации, цена
  (CZK, exponent 2 — ISO 4217; «V textu» → цена nil с причиной),
  локация (город + PSČ), выдержка описания.
- Честные NULL (ТЗ §0.4): координаты, площадь, комнаты **не публикуются
  на странице категории** — site отдаёт лишь примерную локацию
  («Přibližná lokalita») на детальной странице; выгрузка деталек —
  расширение этапа 9 (phone-agent / detail-коннектор).
- Явные ошибки (ТЗ §0.2): фильтры цены/площади → ошибка с причиной;
  неизвестные deal_type / property_type → ошибка со списком поддерживаемых.
- Вежливость: пауза между страницами `scan.page_delay_ms` (config,
  по умолчанию 1000 мс); описательный User-Agent.
- Честная полнота (ТЗ §8.2.1): HTTP 429 → `http_429`; 403/401 →
  `captcha` (если тело похоже на проверку), иначе `network`; любой
  иной не-2xx → `network`; неожиданная кодировка → `layout_change`;
  верстка изменилась (нет карточек при total>0 / нет счётчика /
  неизвестный формат цены) → `layout_change`; страница не загрузилась на
  середине → `partial` с типом; выдача закончилась раньше счётчика
  (объявления удалили во время скана) → остановка; пустая категория →
  честная пустая выдача (Runner пометит `partial` — пустая выдача не
  отличима от сбоя, который не дал ни строчки).

### scan_runs с честным completeness (ТЗ §8.2.1)

- `internal/scan/runner.go`: `Runner.Run` — проверка источника
  (state=active, cooldown, страна), запись `scan_runs` (running →
  терминальное complete/partial/failed + failure_kind +
  listings_found/new_objects), вызов коннектора, запись результатов
  одной транзакцией, завершение скана.
- `complete` — только непустая выдача без ошибки/капчи. `partial` /
  `failed` — неполный скан **не участвует** в вычислении исчезновений
  (этап 6 читает только `complete`).
- Запись: `raw_listings` (неизменяемое наблюдение: price_minor,
  currency, area, rooms, property_type, geom (PostGIS GeogPoint, nil
  без координат), address, posted_at, attributes, description_original,
  fetched_at), затем сопоставление с `objects` (ТЗ §8.1).
- Дедупликация (ТЗ §8.1): радиус 50 м (config `dedupe.by_country`),
  допуск площади 10% (допущение исполнителя), сходство нормализованных
  адресов 0.9; совпадение только по адресу →
  `match_confidence='low'`. В рамках одного скана дубли по
  (source_id, external_id) не записываются повторно.
- `objects`/`price_history`: цена фиксируется на дату наблюдения
  (fetched_at), валюта — из карточки (CZK); `last_seen_at`
  обновляется.

### Сквозной путь (критерий этапа)

- `pb scan -source bazos-reality -search-config 11` — прогон сканера
  по одному источнику и конфигурации поиска; `pb scan -list` — список
  зарегистрированных коннекторов.
- Итог всегда фиксируется в `scan_runs` (complete/partial/failed +
  failure_kind); exit code 0 = «скан выполнен и зафиксирован», а не
  «выдача была полной» — для автоматизации (этап 11) источником
  истины является таблица scan_runs.
- Е2Е-проверка: полный скан категории «продажа → квартира» (byt) —
  результаты ниже.
- Тесты: юнит-тесты парсера (карточки, счётчик, цены, даты, annotate,
  валидация Scan) и `TestScanPipeline` (9 сценариев: полный/неполный
  скан, дубли, дедупликация по радиусу/адресу, partial-скан не меняет
  статусы, тот же источник + тот же адрес + другой external_id →
  отдельный объект) — прогоняются против живой БД (PB_TEST_DSN), фикстуры
  чистятся в t.Cleanup.

## Результаты сквозного скана

### Первый промышленный прогон (run 20) — выявил два дефекта

Полный скан `/prodam/byt/` (384 страницы, пауза 1 с/страницу):
`completeness=partial, failure_kind=layout_change, listings=7677,
new_objects=925`. Итог честный (скан сам пометил себя неполным), но
разбор показал, что неполнота — не в сети, а в двух дефектах
исполнителя:

1. **Нераспознанные «бесценовые» токены.** 8,8% объявлений на
   источнике (675 из 7 677) не несут числовой цены: «Dohodou»
   (по договорённости), «V textu» (в тексте), «Nabídněte»
   (сделайте предложение), «Zdarma» (бесплатно). Первоначальный
   парсер знал только «V textu» и помечал остальные как «цена в
   неизвестном формате» → ложный layout_change (373 карточки).
   Полным сбором по всем 384 страницам категории «byt»
   (7 677 карточек, 2026-08-27) установлен полный словарь
   состояний: Dohodou — 309, V textu — 302, Nabídněte — 54,
   Zdarma — 8, Nerozhoduje — 2 (последнее — значение не
   идентифицировано, контекст карточек не изучался).
   **Исправление:** словарь `noPriceTokens` в коннекторе — эти
   состояния дают `PriceMinor = nil` (честный NULL, ТЗ §0.4), а не
   ошибку; любое *другое* нераспознанное состояние и отсутствующий
   div цены по-прежнему → layout_change (ТЗ §8.2.2).
2. **Сливание объявлений одного источника в один объект.** Адрес
   источника — только «город + PSČ»; адресная дедупликация (ТЗ §8.1 —
   «записи из **разных** источников») не исключала объекты с
   объявлениями того же источника, и все квартиры одного почтового
   района сливались в один объект: 7 677 объявлений → 925 «объектов»,
   `price_history` (548 строк) смешивала цены разных квартир.
   **Исправление** (`internal/scan/match.go`): кандидатом в
   дедупликацию не может быть объект, у которого уже есть объявление
   входящего источника — внутри источника идентичность
   `(source_id, external_id)`. Меж-источниковое сопоставление
   (geo/address, confidence low) не затронуто.

Регрессии покрыты тестами: `TestParseCardNoPriceTokens`,
`TestParseCardMissingPriceDiv` (коннектор) и сценарий 9
`TestScanPipeline` (тот же источник, тот же адрес, другой
external_id → отдельный объект).

Данные run 20 (925 objects, 7 677 object_listings, 7 677 raw_listings,
548 price_history, строка scan_runs) удалены как невалидный
разработочный артефакт: серия цен, смешанная по чужим квартирам,
навсегда отравила бы модель (этап 5). Удаление зафиксировано в этом
отчёте, а не замаскировано.

## Не реализовано и почему

- **Координаты объектов** — сайт публикует только примерную локацию на
  детальной странице (ссылка на карту «Přibližná lokalita»); страница
  категории координат не содержит. Выгрузка деталек — расширение этапа 9
  (там же — полный адрес с улицей). Пока `geom` в objects — NULL
  (честно, ТЗ §0.4).
- **Площадь и комнаты** — не публикуются в карточке категории (есть
  только в тексте описания); парсить свободный текст — источник
  ошибок, поэтому поля nil.
- **Фильтры цены/площади** в search_configs для этого источника —
  robots.txt запрещает URL-параметры (`?cenaod=`, `?cenado=`, …), а
  клиентская фильтрация искажала бы детектирование исчезновений
  (ТЗ §8.2) — коннектор возвращает явную ошибку.
- **IT/NL-атрибуты** в реестре — только по фактическому разбору
  агрегаторов (ТЗ §6), не «по памяти».
- **Аренда (pronajmu) и другие категории** — механизм один
  (deal_type × property_type), но прогнаны не все комбинации: критерий
  этапа — сквозной путь по одному конфигу (выбран продажа/квартира —
  крупнейшая категория, 7 000+ объявлений). Остальные категории
  запускаются созданием search_configs без правки кода.

## Допущения

- **Каноническая таксономия property_type** (flat, house, land, garage,
  office, cottage, space, project, restaurant, warehouse, garden, other)
  — допущение исполнителя: ТЗ не задаёт список; маппинг на категории
  bazos (byt/dum/pozemek/garaz/kancelar/chata/prostory/projekty/
  restaurace/sklad/zahrada/ostatni) подтверждён на сайте 2026-08-27.
  Аренда bazos имеет и «podnajem» — в таксономию не входит.
- **`area_tolerance_pct: 10`** и **`address_similarity: 0.9`**
  (config `dedupe.by_country`) — допущения исполнителя (ТЗ §8.1 задаёт
  только радиус 50 м); значения меняются в конфиге.
- **Число страниц из счётчика** — окно ссылок пагинации на странице
  неполное (ближайшие страницы), поэтому полный скан по ссылкам
  невозможен; доверие счётчику «z N» — единственное работоспособное
  решение для полного обхода.
- **CZK exponent 2** (халержи) — ISO 4217; цена ×100 при записи.

## Заглушки

- Нет. Коннектор — реальный (живой HTTP, реальный HTML), Runner —
  реальный (реальная БД). `ErrNotImplemented` на этом этапе не
  используется.

## Требует ручной проверки

- **Сквозной скан** (результаты в разделе выше) — проверить, что
  `scan_runs.completeness = complete`, `raw_listings` ≈ счётчику сайта,
  объекты в дашборде («Объекты» → цена CZK, статус, адрес).
- **Остальные категории** (dum, pozemek, …; pronajmu) — создать
  search_configs и прогнать (без правки кода).
- **Детальные страницы** (координаты, площадь, полный адрес) —
  расширение этапа 9.
- **Изменения вёрстки** — коннектор честно сломается (layout_change),
  но без уведомления: алерты по failure_kind — этап 8.

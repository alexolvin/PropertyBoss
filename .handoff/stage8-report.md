# Отчёт этапа 8 — Telegram-бот + триггеры уведомлений (ТЗ §2, §3.2, §8.2, §9.4)

Дата: 2026-09-02. Команды: `pb notify send | test | object | check-disk | status`
(см. «Результаты на реальных данных»).

## Реализовано

### 1. Пакет `internal/notify/` — очередь, доставка, рендер

| Файл | Содержимое |
|---|---|
| `notify.go` | `DB` (интерфейс: пул и транзакция), `Enqueue`, `PendingCount`, `Flush`/`flushOne` (FOR UPDATE SKIP LOCKED, одна транзакция на строку), `ErrPermanent`, `QueueStatus`/`Status` |
| `telegram.go` | `Client` (Bot API, только `sendMessage`), `Send`: до 3 попыток; 429 → пауза `Retry-After` (потолок 60 с) и повтор; 5xx/сеть → повтор с бэкоффом 1 с / 2 с; прочие 4xx → `ErrPermanent` (неверный токен, чат не найден — ретраем не лечится); `RateLimitWait` |
| `render.go` | `Render(kind, payload)`: 5 видов (delist_anomaly, disk_low, liquidity_model, object_snapshot, test); обязательные поля payload — проверка, пропуск = ошибка, а не «разумное значение по умолчанию»; деньги — `internal/money` (экспонента из справочника `currencies`), разряды пробелами; nil-метрики — «н/д», nil-оценка/вероятность — машиночитаемая причина, а не умолчание |
| `disk.go` | `MeasureDisk` (`syscall.Statfs`, свободное = `Bavail`, не `Bfree`: резерв ядра не считается доступным), `CheckDisk` (порог + окно повтора) |
| `object.go` | `ObjectSnapshot`/`ObjectSnapshotFor` — последняя оценка и последняя оценка ликвидности объекта (LATERAL по `computed_at`), `Payload()` для рендера |

**Критерий этапа 8** («Уведомление содержит интервал и размер выборки,
а не голое число») выполнен структурно: каждый модельный выход в тексте
сопровождён выборо́й, по которой он посчитан. Примеры:
- публикация модели: «Выборка: N завершённых событий (порог M), K
  person-period строк (P параметров). Разбиение по времени: T строк
  обучения (до даты) / T′ строк проверки. Валидация: C-index, Brier,
  макс. отклонение калибровки. Переход из статуса: …»;
- снимок объекта: «Оценка: отклонение от модели ±X%; интервал A — B;
  выборка n=N (r²=…, модель …)», «Вероятность ухода с рынка за H дн.:
  P% (модель …, K событий в обучении)»;
- delist-аномалия: «исчезло C из A активных объектов (X%), порог Y%»
  + ссылка на защиту №3 (ТЗ §8.2) и указание, что статусы НЕ применены;
- диск: «свободно X% (F из T GiB), порог Y%» + ссылка на ТЗ §3.2.

**Доставка (ТЗ §3.4).** `Flush` берёт строки по одной
(`FOR UPDATE SKIP LOCKED`), на каждую — отдельная транзакция:
claim → Render → Send → status `sent`/`failed` (+ текст ошибки, обрезка
до 1000 зн.). Сбой на строке не глотает прогон; `ErrPermanent`
останавливает прогон — дальше по очереди ситуация та же (битый токен/
чат), и оператору это видно одной ошибкой. Частичная обработка —
нормальный исход cron-точки: недоставленное остаётся `pending`.
Дубль при сбое между отправкой и коммитом допустим (лучше дубль, чем
потерянного алерта нет; идиотизма ради алерт не отправляется дважды).

### 3. Миграция `0021_notify.sql`

`notifications.created_at TIMESTAMPTZ NOT NULL DEFAULT now()` — время
**постановки** в очередь. Окно повтора disk-алерта считается от него, а
не от отправки: если отправка сломана (нет токена), очередь не должна
заполняться дублями при каждом проверочном прогоне. Аудит: видно, когда
событие зафиксировано, а не только когда доставлено. Применена
(`pb migrate`, 2026-09-01).

### 4. Конфиг — блоки `telegram:` и `notify:`

| Ключ | Значение (example) | Валидация |
|---|---|---|
| `telegram.enabled` | false | при `true` — token и chat_id обязательны |
| `telegram.token` / `telegram.chat_id` | "" | не дублируются в коде и логах |
| `telegram.base_url` | `https://api.telegram.org` (дефолт) | parse-ится как http(s) URL с hostом (подмена для тестов/прокси) |
| `notify.flush_limit` | 100 | ≤ 0 → 100 |
| `notify.disk_path` | "" | пусто = check-disk отключён (явная ошибка при вызове) |
| `notify.disk_critical_pct` | 10 | безусловно ∈ (0, 100) |
| `notify.disk_realert_minutes` | 1440 | ≥ 0 (0 = повтор каждый раз при пороге) |

Блоки — в `config/config.example.yaml` и локальном `config/config.yaml`
(там `enabled: false`, token/chat_id пусты — реальный токен кладёт
оператор, файл в .gitignore).

### 5. CLI — `pb notify` (cmd/pb/notify.go)

- `send [--limit N]` — **cron-точка** (ТЗ §3.4): доставить pending-очередь;
  пустая очередь → «очередь пуста» (успех); Telegram не настроен при
  непустой очереди → явная ошибка, строки остаются pending.
- `test` — тестовое сообщение (проверить токен/чат/сеть).
- `object <id>` — снимок объекта (цена, срок на рынке, последняя оценка
  с интервалом и n, вероятность ухода с горизонтом и числом событий);
  работает и без токена (консоль).
- `check-disk` — замер всегда печатается; в очередь — только при пороге
  и вне окна повтора.
- `status [--limit N]` — pending/sent/failed + последние строки
  (создано/отправлено/ошибка).

### 6. Live-тесты ликвидности: гейт §9.4 покрыт ассертами

`internal/liquidity/liquidity_test.go`:
- `TestRunLiveInsufficientHistory` — после прогона в очереди **0**
  уведомлений (неоткалиброванная модель ничего не шлёт);
- `TestRunLiveTrainPredict` — после публикации **ровно 1**, после
  повторного прогона опубликованной модели — **всё ещё 1** (без дубля).
- `liqCleanup` дополнительно чистит sandbox-уведомления

## Результаты на реальных данных

(локальная БД, 2026-09-02; реального токена нет — поведение без токена
проверено как часть этапа, см. ниже)

```
pb notify status    → pending=0 sent=0 failed=0
pb notify check-disk → /home/user/myhub — свободно 87.2% (397.9 из 456.3 GiB), порог 10%
                       порог не достигнут
pb notify object 946 →
  📋 Объект 946 (CZ/sale, active): цена 14 500 000 CZK, на рынке 5 дн.
  Оценка: нет — no_area.
  Вероятность ухода с рынка: нет — insufficient_history.
  notify object: в Telegram не отправляю (Telegram не настроен …)
pb notify send      → очередь пуста
pb notify test      → «Telegram не настроен (telegram.enabled/token/chat_id) —
                       уведомления копятся в очереди…» (exit 1, явная ошибка)
```

Контекст данных (честно): на 2026-09-02 все 7762 строки `valuations`
— отказы (price_deviation NULL, преобладает `no_area` — см. отчёт
этапа 5), модель ликвидности — `insufficient_history` (0 строк
с вероятностью, холодный старт — отчёт этапа 7). Поэтому полный
вариант снимка («отклонение + интервал + n») на **реальных** данных
показать нельзя — покрывают его unit-тест
`TestRenderObjectSnapshotFull` и live-тест `TestLiveObjectSnapshot`
на песочных данных; на реальных — только ветки «нет — причина»,
которые и отображаются выше. Очереди `notifications` реальная — пустая:
аномалий delist не было (отчёт этапа 11), disk-порог не достигнут,
модель не опубликована.

## Не реализовано и почему

- **Доставка реальным токеном.** Токен выдаёт @BotFather (решение
  пользователя); `config.yaml` в .gitignore, в репо и в коде токена
  нет. Весь путь до Bot API покрыт mock-сервером (URL, тело, 429/5xx/
  4xx), последний метр — до api.telegram.org — «Требует ручной проверки».
- **Периодический запуск `pb notify send`.** Это cron-точка (ТЗ §3.4 —
  самодостаточная пакетная задача); демон/cron — часть развёртывания на
  vzu5-omi (этапы 12–13), как и для `pb schedule run`.
- **Диалоги/команды в боте.** ТЗ §2 прямо: бот — только уведомления,
  без диалога. Входящие сообщения не обрабатываются намеренно.

## Допущения (ТЗ §0.2)

1. **Язык сообщений — русский**: получатель — оператор, ТЗ и вся
   документация проекта на русском.
2. **Дубль при сбое между отправкой и коммитом** допустим (ТЗ §3.4
   требует устойчивости к срамам; потеря алерта хуже дубля).
3. **Окно повтора disk-алерта — от `created_at`** (постановки), не от
   `sent_at`: сломанная отправка не должна затапливать очередь
   (миграция 0021).
4. Свободное место — `Bavail` (free + reclaimable), не `Bfree`:
   резерв ядра (~5%) оператором недоступен.
5. 3 попытки на сообщение, бэкофф 1 с/2 с, `Retry-After` с потолком
   60 с, таймаут запроса 30 с — значения реализатора (ТЗ не фиксирует).
6. `flush_limit=100`/прогон, `disk_critical_pct=10`,
   `disk_realert_minutes=1440` — значения оператора (ТЗ §3.2 требует
   алерт ДО критической точки, числа не предписывает).
7. `object_snapshot` идёт прямой отправкой, минуя очередь: это запрос
   оператора «покажи», а не событие; дублировать его в `notifications`
   нечем (строка означила бы доставку, которой нет).
8. `MeasureDisk` — `syscall.Statfs` (стандартная библиотека): целевая
   ОС — Linux (Termux); на других ОС пакет не скомпилируется — это
   осознанное ограничение платформы проекта.

## Заглушки

Нет. Все функции рабочие; очередь/клиент/рендер/диск/снимок покрыты
тестами до настоящего Bot API (mock на httptest). Единственная внешняя

## Требует ручной проверки

1. **Реальная доставка**: заполнить `telegram.token`/`chat_id`
   (enabled: true), `pb notify test` → «тестовое сообщение доставлено»,
   затем `pb notify send`.
2. **`disk_path` на целевом устройстве** (vzu5-omi): замер проверен на
   этой машине (`/home/user/myhub`, 456 GiB); реальный путь и порог —
   решение оператора на этапе 12–13.
3. **Настоящее срабатывание disk-порога**: на этой машине свободное 87%,
   порог 10% — ветка «алерт поставлен» покрыта live-тестом с порогом
   99.99% (алерт гарантирован), но реальный переполненный диск не
   форсировался.
